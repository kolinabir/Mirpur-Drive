## Bug fix, ~20:05: poles didn't collapse (code-only, no browser check per
## owner instruction — "Don't check live. Just find a code and fix.")

Owner report: "doesnt collapse". Traced without running it, by reading
drive.js's own collision code against destructibles.js's impact test.

**Root cause found**: `tryHit()` tested the distance from the CAR'S
CENTRE (`player.position`, which drive.js keeps at the car's true centre
while driving — src/drive.js:1022) to each pole against a small
`IMPACT_RADIUS` (1.15 m). That can only be true if a pole ends up almost
exactly under the car's midpoint. But drive.js's own collision (the corner
loop at src/drive.js ~950-970) already pushes the car's four CORNERS out
to stay >= 0.9 m from any wall segment; corners sit 2.2-2.4 m from the
centre (HALF_L=2.2, HALF_W=0.9), and a thin pole usually passes BETWEEN two
corners without the centre ever getting near 1.15 m away. So the check
almost never fired regardless of how directly the pole was clipped.

**Fix**: `tryHit()` now recomputes drive.js's own four corner points from
the car's position and yaw — the EXACT same `fwd`/`rgt`/HALF_L/HALF_W
construction drive.js uses for its own resolveCollision calls — and tests
each corner against the pole using the SAME 0.9 m radius drive.js's
resolveCollision uses (`CORNER_PUSH_RADIUS`, plus a small
`POLE_RADIUS=0.2` margin for the pole's own half-extent). A corner
currently being pushed away from a pole sits very close to that radius
from it, so this test now matches ground truth instead of guessing a
margin from outside drive.js. A secondary rectangle-vs-centre check
(`along`/`across` against `CAR_HALF_L`/`CAR_HALF_W`) covers the case of a
pole struck dead-centre on the front/rear edge, between the two corners on
that end, which no single-corner test catches.

Also checked (no change needed): drive.js sheds car speed to 15% ON THE
SAME FRAME it detects a corner hit, but only AFTER computing that frame's
position update from the pre-impact speed — so the frame-to-frame position
delta destructibles.js uses to estimate speed still reflects the
full approach speed on the actual impact frame, not the post-impact
crawl. `IMPACT_MIN_SPEED` (2.5 m/s) should therefore still gate correctly.

## Second bug fix, ~20:20: pole collision still didn't work + car was
## slowed (code-only, no browser check — owner: "dont slow vihincale! any
## speed should collabse or break it")

**Root cause of the slowdown**: `src/drive.js` runs its OWN
`requestAnimationFrame` loop (`src/drive.js:1143`), entirely independent
of main.js's frame loop that drives `destructibles.update()`. drive.js's
own `stepCar()` sheds 85% of the car's speed
(`car.speed *= 0.15`) the INSTANT a corner is found within its 0.9 m
collision radius of any wall segment — including a pole's — inside its own
single function call, before destructibles.js ever runs. Reacting to a
contact drive.js has already resolved is always at least one frame late:
even with the corner-radius fix from the previous pass, by the time the
pole's collider was removed, drive.js had already shed the speed for that
frame.

**Fix**: detect and destroy the pole at a radius LARGER than drive.js's
own 0.9 m push radius (`PRE_EMPT_MARGIN = 1.3 m`, `src/destructibles.js`),
so the collider is gone from the grid while the car's corner is still
comfortably outside the distance drive.js's own physics would ever react
to. At the car's top speed (22 m/s) a 60 fps frame covers ~0.37 m, so this
buys several frames of lead time. This does not make the race impossible
in principle (the two loops are still independent rAF callbacks with no
guaranteed ordering — an extreme frame hitch could still let drive.js see
the pole first), but it makes the window it would need to win vanishingly
small at any speed reachable in the corridor. Also dropped
`IMPACT_MIN_SPEED` from 2.5 m/s to 0.05 (kept only to stop a perfectly
stationary car resting on a pole from re-triggering every frame) — any
actual approach now collapses the pole, matching "any speed".

Trade-off, stated plainly: with a ~2.4 m detection radius from each
corner, a pole roughly up to ~4.5 m ahead of the car's centre can now
topple slightly before the car visually reaches it, rather than exactly on
contact. That is the deliberate cost of guaranteeing no speed loss with
two independent frame loops; if it now looks like poles fall too early,
the fix is to reduce `PRE_EMPT_MARGIN`, which reopens some risk of the
original one-frame slowdown returning.
