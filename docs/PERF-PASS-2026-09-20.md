# Performance pass, 2026-09-20: "FPS drops and laggy" on the live build

Owner report after the first Cloudflare deploy: frame drops and lag. Target:
a steady 60 fps.

## How it was measured

`requestAnimationFrame` timing is useless in a backgrounded preview pane (it
is throttled to 1 Hz under load), so GPU cost was measured synchronously:
render N frames back to back, then force a sync with a 1-pixel `readPixels`,
and divide. Medians of 5 rounds x 8 frames, Apple M4, 1600x900 CSS px. CPU
systems were timed by wrapping each `update()` on `window.__mirpur`.

## What was found

The frame was **GPU fill-rate bound**, not CPU bound.

| | before | after |
|---|---|---|
| JS systems (metro, traffic, peds, minimap, ...) | ~3 ms | ~3 ms |
| three.js submission (`renderer.render` CPU side) | ~6.5 ms | ~3 ms |
| **GPU, Pallabi spawn** | 12-13 ms | **3.8-4.9 ms** |
| **GPU, Mirpur 10 golchokkor** | 18.9 ms | **5.3 ms** |
| **GPU, Mirpur 11 road** | 30.2 ms (worst seen) | **4.4 ms** |
| **GPU, Benarasi Palli** | 19.0 ms | **4.3 ms** |
| minimap patch regen (every 150 m travelled) | **44 ms stall** | 0.5-4 ms |

Things that were checked and are NOT the problem: triangle count (the stadium
view draws 916k triangles in 2.9 ms), transparent overdraw, the light count
(3), tile streaming (<= 2.6 ms per tile build), draw calls (250-560).
Replacing every material with `MeshBasicMaterial` only got the old build to
11 ms, so PBR shading was a minority of the cost: the bulk was 4x MSAA
resolving a 2800x1575 drawing buffer.

## What changed

1. **MSAA only on low-DPI screens** (`devicePixelRatio < 1.5`). On a 2x
   display it bought nothing visible and was the single largest cost.
2. **Pixel ratio cap 1.75 -> 1.5**, and then
3. **an adaptive resolution governor** (`src/perf-governor.js`): every 750 ms
   of gameplay frames it drops the pixel ratio by `sqrt(target/avg)` when the
   average frame is over ~17.25 ms, and probes back up (with exponential
   back-off, 5 s -> 60 s) when there is headroom. Floor 0.8x on hi-DPI, 0.7x
   otherwise. Simulated against fast / medium / slow / recovering GPU models
   it lands on 60 fps in every case and returns to full resolution when the
   load goes away. The HUD stats line now ends with the live ratio (`1.50x`).
4. **Minimap patch regen** (`src/map/map-raster.js`): a 100 m spatial index
   over buildings and road segments replaces the walk over all ~30k
   footprints, and footprints are filled in batches of 128 instead of one
   giant path.

Overrides for A/B testing: `?aa=1` / `?aa=0`, `?res=fixed`.

## Still true / not done

- A GPU too slow to hit 60 fps at the 0.7-0.8x floor will still miss it; the
  next lever would be a shorter `LOD_TILE_VISIBLE_RANGE` tier driven by the
  same governor.
- `interior.update()` spikes ~13 ms once, the first time a station interior
  is approached (it builds on demand). Not fixed.
- First sight of a new material still costs a shader compile (136 programs
  in a session). `renderer.compileAsync` at load would hide that.
- Every object has `matrixAutoUpdate = true` (1487 objects); freezing the
  static ones is a small, safe CPU win left on the table.
